## 调查结论

2026-10-08，两次读取同一输入框确认显示内容与内部内容不一致：

| 检查项 | 观察结果 |
| --- | --- |
| 输入框 `innerText.length` | 928，四个非空英文段落 |
| DOM 段落结构 | 七个段落节点，仅一个 `data-block` 容器，段落共享一个 `data-offset-key` |
| 编辑器内部内容 | `stateNode._latestEditorState` 和 `stateNode.props.editorState` 均为 307 个字符、一个块 |
| 内部内容对应位置 | 与可见输入框最后一个段落完全相同，不等于全文 |
| 当前中文残留 | 当前可见内容与所检查的内部内容均未发现中文 |

因此当前草稿已经存在状态同步异常，不能根据屏幕全文判断实际提交内容。本次没有发帖或捕获发帖请求，不能断言最终提交一定只含最后一段，也不能把当前状态等同于此前重复回复的全部触发链。

## 2026-10-08 初次代码证据与推断

- [回填实现](../../apps/extension/src/x-dom.ts)的 `replaceEditorText` 只在操作前校验可见文本，之后以 DOM Range 选中内容并执行 `execCommand('insertText')`。命令失败时直接覆盖 `textContent`，再派发人工 `input` 事件。
- 该函数在前置校验通过后直接返回成功，没有等待编辑器重渲染或验证内部内容。[采用和撤回入口](../../apps/extension/src/x-ui.tsx)据此立即提示成功。撤回也复用同一函数。
- [UI 测试](../../apps/extension/src/x-ui.test.tsx)将 `execCommand` 固定模拟为失败，以普通可编辑元素验证显示文本；[DOM 测试](../../apps/extension/src/x-dom.test.ts)覆盖操作前草稿冲突，没有真实 Draft 编辑器多段落状态同步的验证。
- [扩展入口](../../apps/extension/entrypoints/x.content.tsx)中的 DOM 观察器维护按钮，未发现它主动反复采用译文的路径。

最有力的根因方向是回填方式破坏了 X 受控编辑器的块结构或状态同步。当前残留的 Draft 包装与重复段落标识更符合原生命令改动 DOM 后没有正确同步块结构的路径；本次未观察采用发生时的事件，不能确定当次命令返回值或排除后续事件的影响。直接覆盖 `textContent` 的备用路径同样缺少同步保证。

用户描述的重新粘贴恢复正常，与真实粘贴经过编辑器处理并重建内容结构的解释一致；这是机制推断，本次未改动用户草稿验证。
